A task's journey

  1. Submit. The API validates the task, applies namespace quotas, and inserts it as QUEUED. A trigger sends a NOTIFY so the leader wakes immediately. (Writes the leader makes itself, such as workflow steps, retries and schedule runs, wake its dispatcher directly instead: NOTIFY serializes commits, so the leader avoids it on its hot path.)
  2. Claim. The leader works out the free slots on its workers and the distinct label sets they have, then claims up to that many due tasks in one statement: SELECT … FOR UPDATE SKIP LOCKED ordered by a precomputed dispatch key (priority with aging, then due time). The same statement enforces queue concurrency limits, queue rate limits, token-per-minute limits, namespace concurrency limits, and the rule that some free worker must have every label the task requires. Claiming increments the task's attempt.
  3. Dispatch. Each claimed task goes to a worker that accepts it (has its labels, is not draining, has a free slot), round-robin by worker ID, over gRPC. A worker that refuses or can't be reached gets the task requeued.
  4. Run. The worker runs the task with a minimal environment, captures its output (capped, keeping the beginning and the end), and keeps it readable live for task logs -f.
  5. Report. The worker reports the result for its attempt. The leader records it only if the attempt still matches; a report for an old attempt is counted as stale and ignored.
  6. Retry or finish. A failure with retries left goes back to QUEUED with a delay of retry_delay × 2attempt (capped at an hour), or later if a model provider sent Retry-After. Permanent failures and exhausted retries end FAILED and appear in the dead-letter queue. The previous attempt's worker, timing, error and output are kept in the attempt history.

Leader election

Run two or more coordinators. Each campaigns once a second for a Postgres advisory lock with pg_try_advisory_lock; the one holding it is the leader. Advisory locks belong to a database session, so when the leader dies, its connection closes, the lock is released, and a standby acquires it within about a second.

  • Takeover. The new leader bumps the epoch in the coordinator_leader row, then rebuilds its view from Postgres: workers from the workers table, in-flight tasks from the tasks table. Work in flight keeps running on workers and reports to the new leader.
  • Finding the leader. Standbys answer every call with a "not the leader" error naming the leader's address. The client library (used by the API and workers) follows the redirect, and while an election is in progress it cycles through the configured coordinator addresses until one answers as leader.
  • Liveness. The leader updates a heartbeat on its row; a leader whose heartbeat is older than five seconds is not advertised to clients.

Fencing: stale actors change nothing

Two kinds of actor can be wrong without knowing it: a leader that has been deposed but hasn't noticed yet, and a worker that was partitioned away while its task was retried elsewhere. Conductor fences both.

The chaos suite partitions a worker mid-task, waits for the task to be retried as attempt 2, heals the partition, and checks that attempt 1's report is ignored and attempt 2's output is the one recorded.

The nightly chaos suite runs a steady load of tasks and sagas through each of these (plus Postgres latency injected with Toxiproxy) and then checks the invariants: no task lost, none stuck, every workflow terminal, compensation run exactly where required.

How workflows run

A workflow run is a snapshot of its definition plus a row per step. The coordinator's reconciler is a pure function of that state: given which steps completed, failed or are waiting, it decides what to start next. It runs when a step's task finishes, and a periodic sweep re-runs it for every active run, so a missed event can never strand a run.

  • A step starts once all its depends_on steps completed; independent branches run in parallel.
  • When a step fails for good (or the run is cancelled), running steps are cancelled and every completed step with a compensation is undone, in reverse dependency order. Each compensation sees its own step's outputs.
  • Approval and signal steps are waits, not tasks: they hold no worker while they wait for a person or a system, and a timeout decides what happens if nobody answers.
  • Agent steps are state machines over tasks: each model call and each tool call is its own task with an idempotency key, so a crash resumes from the last finished call.
  • Because the run keeps the definition snapshot it started with, applying a new version never changes runs already in flight.

How schedules fire

Schedules live in Postgres with their next run time. The leader claims due schedules with FOR UPDATE SKIP LOCKED, starts the task or workflow, and records the next run in the same transaction, so a run time fires at most once even across restarts and failovers. When the leader was down at a run time, the schedule's misfire policy decides: skip it, run_once to catch up with a single run, or catch_up on every missed slot.

Migrations are embedded in the binary, applied on startup under an advisory lock, and forward-only. The schema also carries conductor_slot_demand(), which autoscalers call to read queue depth (see autoscaling).

Design decisions

  • Push dispatch, scheduling in the leader (ADR 0001): workers never hold database credentials, and the per-task cost is Postgres work either way.
  • A dashboard of plain JavaScript modules embedded in the binary (ADR 0002): no build step, nothing to deploy separately.
  • AI calls are ordinary tasks (ADR 0003): they inherit retries, limits, cancellation and tracing.
  • Kubernetes as a home, not a dependency (ADR 0004): task pods through a small REST client, autoscaling from a SQL function, an operator that only uses the HTTP API.

The records are in docs/adr in the repository; DEVLOG.md tells the story of each phase with diagrams.
