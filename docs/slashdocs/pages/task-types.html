At a glance

Every step of a workflow, and every task, has a type. Five types run as tasks on workers; three are workflow-only steps that wait or orchestrate.

TypeRunsWhereOutputs
shell (default)A command with sh -cAny workerLines written to $CONDUCTOR_OUTPUT
httpOne HTTP requestAny workerstatus, body
containerA Docker container, to completionWorkers with the Docker socketNone (output is the container's logs)
k8sA Kubernetes pod per attemptThe Kubernetes task poolLines written to $CONDUCTOR_OUTPUT (4 KB)
llmOne model callWorkers with a model configuredtext, or the schema's fields
approval (steps only)Nothing: waits for a personNo workercomment, decided_by
signal (steps only)Nothing: waits for a systemNo workerThe signal's fields
agent (steps only)A model with tools, in a loopModel calls on model workers, tools on shell workersanswer

Workers advertise a type.<name> label for each type they can run, and a task is only dispatched to a worker that advertises its type. A step has the settings of its own type and no others; mixing them (say, run and http) is rejected.

shell

- name: backup
  run: |
    pg_dump "$DATABASE" | gzip > /backups/$(date +%F).sql.gz
    echo "file=/backups/$(date +%F).sql.gz" >> "$CONDUCTOR_OUTPUT"
  env: {DATABASE: "${{ inputs.database }}"}
  timeout: 30m

The command runs with sh -c on the worker, as the worker's unprivileged user, in the minimal task environment. Cancellation and timeouts kill its whole process group. As a standalone task: conductorctl task submit -cmd '...'.

http

- name: notify
  type: http
  http:
    method: POST                                  # GET (default), POST, PUT, PATCH, DELETE, HEAD
    url: https://hooks.example.com/orders/${{ inputs.order_id }}
    headers: {Authorization: "Bearer ${{ steps.login.outputs.token }}"}
    body: '{"status": "shipped"}'                  # Content-Type defaults to application/json
    expect_status: [200, 202]                      # default: any 2xx

The task succeeds when the response status is expected. Its outputs are status and body (when the body fits in 64 KB), and its output is the status line plus the body. URL, body and headers may use expressions. Standalone: conductorctl task submit -url URL -method POST -body '{...}' -header K=V.

container

- name: transcode
  type: container
  container:
    image: jrottenberg/ffmpeg:6.1-alpine
    command: ["-i", "${{ inputs.source }}", "/out/video.mp4"]
    memory: 512m          # k, m or g
    cpus: 1.5
    network: none         # bridge (default) or none

Runs a Docker container to completion on a worker that can reach the Docker daemon (CONDUCTOR_DOCKER_SOCKET), pulling the image if needed, and removes it afterwards, also when cancelled. The task's environment is passed in; the output is the container's logs. Because access to the Docker socket is equivalent to root on the host, such workers are opt-in (docker compose --profile containers). On Kubernetes, use k8s instead.

k8s

- name: report
  type: k8s
  k8s:
    image: ghcr.io/acme/reports:1.4
    command: [python, -m, reports]                 # replaces the image's entrypoint
    args: [build, "${{ inputs.day }}"]
    cpu: 500m                                      # request and limit
    memory: 512Mi                                  # request and limit
    service_account: reports-reader                # optional; must be allowed
    node_selector: {cloud.google.com/gke-spot: "true"}
    run_as_user: 1000                              # optional; default 65534

Each attempt runs as its own pod, created by the Kubernetes task pool through the Kubernetes API. The worker watches the pod, streams its logs live, and deletes it when the task finishes, times out or is cancelled.

  • Least privilege by default: user 65534, no capabilities, no privilege escalation, the RuntimeDefault seccomp profile, no service-link variables, and no service account token. A task may name only a service account the chart allows (kubernetesTasks.serviceAccounts); naming another fails it permanently.
  • Verbatim strings: command, args and environment reach the container exactly as written; Kubernetes' $(VAR) expansion is escaped away.
  • Outputs use the same $CONDUCTOR_OUTPUT contract as shell steps. Inside the pod that file is the container's termination message, which the kubelet keeps up to 4 KB; larger outputs fail the task rather than arrive truncated.
  • Failing fast: an invalid image name fails permanently; an image that can't be pulled, or a configuration error, fails the attempt. A timeout says when the pod was never scheduled (for example "0/3 nodes have a GPU").
  • Cleanup: task pods are owned by the worker's pod, stop by themselves a minute past their timeout, and are swept up if a worker dies.

Standalone: conductorctl task submit -type k8s -image alpine:3.20 -memory 64Mi -- echo hello. Enable it with kubernetesTasks.enabled in the chart (see Deploying).

llm

- name: classify
  type: llm
  llm:
    model: gpt-4o-mini                             # default: CONDUCTOR_LLM_MODEL
    system: You triage support tickets.
    prompt: "Ticket: ${{ inputs.ticket }}"
    schema:                                        # optional: a JSON Schema object
      type: object
      properties: {severity: {type: string, enum: [low, high]}, team: {type: string}}
      required: [severity, team]
      additionalProperties: false
    max_tokens: 300
    temperature: 0

One call to a Chat Completions API (OpenAI, or any compatible server: Ollama, vLLM, LiteLLM, Azure OpenAI). Without a schema the answer is the text output; with one, the model must answer with a matching JSON object and its top-level fields become outputs. Token usage and cost are recorded per task. Rate limits honour Retry-After, and permanent errors (a bad key, an unknown model) skip the retries. Details in AI features.

approval

- name: sign_off
  type: approval
  approval:
    message: "Ship order ${{ inputs.order_id }}?"
    timeout: 24h
    on_timeout: reject            # reject (default) or approve

The run pauses at this step without holding a worker until someone approves or rejects it: conductorctl workflow approve|reject RUN STEP -comment "...", the dashboard's Approvals page, or the API. Approving completes the step with outputs comment and decided_by (the API key's name, or timeout). Rejecting fails it, so completed steps are compensated. conductorctl approvals lists what is waiting.

signal

- name: wait_for_payment
  type: signal
  signal:
    name: payment-confirmed
    timeout: 2h                   # then the step fails

The run pauses until another system sends the named signal to it:

conductorctl workflow signal RUN_ID payment-confirmed -data '{"amount": "42.00", "ref": "pay_123"}'
curl -X POST -H "Authorization: Bearer $KEY" -d '{"amount": "42.00"}' \
  $CONDUCTOR_URL/v1/workflows/RUN_ID/signals/payment-confirmed

The payload's top-level fields become the step's outputs. A signal sent before the run reaches the step is kept for it, so the sender doesn't need to know where the run is.

agent

- name: investigate
  type: agent
  agent:
    prompt: Find out why checkout latency rose this morning, and say what to do.
    system: You are an SRE. Be concise.
    model: gpt-4o-mini
    max_turns: 8                  # model calls (default 10, at most 100)
    max_tool_calls: 30            # default 50
    max_duration: 10m             # default 15m
    budget: {max_cost_usd: 0.25}
    tools:
      - name: recent_errors
        description: The last errors from a service's log
        parameters:
          type: object
          properties: {service: {type: string}}
          required: [service]
        run: tail -n 50 "/var/log/$ARG_SERVICE.log"
        timeout: 1m               # default 2m

The model calls tools in a loop until it answers; the answer is the answer output. Every model call is an llm task and every tool call is a shell task, each created exactly once with its own idempotency key, so if a worker dies mid-run the agent resumes from the last finished call and only the call in flight runs again.

A tool's arguments arrive as environment variables, never in the command line: each top-level argument as $ARG_<NAME>, all of them as JSON in $TOOL_ARGS, with $TOOL_NAME and $TOOL_CALL_ID. The step's env, inputs and run variables are available too. The tool's output is what the model sees. The dashboard shows the whole conversation and every call.
