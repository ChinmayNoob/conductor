Every option needs one thing outside Conductor: a Postgres database (tested with Postgres 16). Conductor creates and migrates its own schema on startup; the user needs to own the database (on managed services, the default application user does).

Building images

Images are not published yet. Build them from a checkout and push them to your registry:

docker build -t REGISTRY/conductor:TAG .                                    # every component, one image
docker build -f operator/Dockerfile -t REGISTRY/conductor-operator:TAG .    # only for the Kubernetes operator
docker push REGISTRY/conductor:TAG && docker push REGISTRY/conductor-operator:TAG

The image is Alpine with bash and time zone data, running as an unprivileged user (UID 10001). Its entrypoint is conductor; the argument picks the component: coordinator, api, worker, dev or mock-llm.

The binary

go build -o bin/ ./cmd/...          # conductor, conductorctl, conductor-bench
CONDUCTOR_CLUSTER_TOKEN=$(openssl rand -hex 32) CONDUCTOR_API_KEY=cnd_$(openssl rand -hex 32) \
POSTGRES_HOST=db.internal POSTGRES_PASSWORD=... bin/conductor coordinator   # :8080
... bin/conductor api                                                        # :8081
... CONDUCTOR_COORDINATOR_ADDR=coord1:8080,coord2:8080 bin/conductor worker # :9000

Every component reads the same environment variables (see configuration), so one environment file can drive them all. Point workers and the API at every coordinator (CONDUCTOR_COORDINATOR_ADDR, comma-separated); they find the leader. Workers advertise their own IP; set CONDUCTOR_WORKER_ADVERTISE_ADDR if the coordinator must reach them at another address. On shutdown (SIGTERM) every component stops gracefully; workers let running tasks finish for CONDUCTOR_SHUTDOWN_TIMEOUT.

Kubernetes: the Helm chart

The chart in deploy/helm/conductor runs a highly available cluster. Defaults are complete for trying it out; production needs a real database and your images:

helm install conductor deploy/helm/conductor -n conductor --create-namespace \
  --set image.repository=REGISTRY/conductor --set image.tag=TAG
kubectl get secret -n conductor conductor-auth -o jsonpath='{.data.api-key}' | base64 -d
kubectl port-forward -n conductor svc/conductor-api 8081:8081
helm test conductor -n conductor      # the API answers and reaches its database

What you get

  • Two coordinators (leader election as everywhere), two API replicas behind a Service with a HorizontalPodAutoscaler, two workers, and a single-pod dev Postgres.
  • Mutual TLS between components with a CA the chart generates. The cluster token, API key, certificates and dev database password are generated on install and kept on upgrades.
  • PodDisruptionBudgets, startup, readiness and liveness probes (/healthz, /readyz on port 9090), resource requests and limits, pods spread across nodes.
  • Non-root pods with read-only root filesystems and no capabilities; a service account token only where it is used.
  • NetworkPolicies: coordinators accept only the API and workers, workers only coordinators, the dev database only coordinators and the API; the API accepts anyone (or networkPolicy.apiFrom).
  • Zero-downtime rollouts: coordinators surge first, workers drain for shutdownTimeoutSeconds, and the API delays its shutdown until load balancers stop sending to it. A rolling restart of everything under load loses no task and fails no request (tested in CI).

Secrets and TLS

  • auth.existingSecret: a Secret with cluster-token and api-key. Empty: generated once and kept.
  • tls.existingSecret: a Secret with ca.crt, tls.crt and tls.key; the certificate's SANs must include tls.serverName (conductor), and it is used as both server and client certificate. Empty: a CA and certificate are generated (valid ten years). cert-manager users point this at a Certificate's secret.
  • Tools that render charts with helm template (Argo CD, Flux with some settings) can't read back generated secrets, so set both and use a real database there; see GitOps.

Worker pools

worker configures the default pool. workerPools adds more, each a Deployment taking worker's settings and overriding some. Every worker gets the label pool=<name>.

worker:
  replicas: 3
  slots: 8                       # tasks per worker
  shutdownTimeoutSeconds: 300    # let tasks up to 5 minutes finish on rollouts
workerPools:
  gpu:
    dedicated: true              # only tasks with labels {pool: gpu}
    labels: {gpu: "true"}
    nodeSelector: {cloud.google.com/gke-accelerator: nvidia-l4}
    resources: {limits: {nvidia.com/gpu: 1}}
    autoscaling: {enabled: true, maxReplicas: 4}

Autoscaling on queue depth

With KEDA installed, autoscaling.enabled on a pool makes a ScaledObject that scales it on demand: tasks the pool could run that are due, plus tasks running on it, divided by its slots. It scales to minReplicas (default 0) when idle.

SELECT conductor_slot_demand('{"pool": "gpu", "gpu": "true", "type.shell": "true"}', '{"pool": "gpu"}')
  • The query is a SQL function shipped with the schema (SECURITY DEFINER), so the scaler can use a database role with no table access, and its settings never depend on the table layout.
  • Make every autoscaled pool but one dedicated: two pools that both take any task would both scale up for the same tasks (the chart refuses that).
  • Tune with pollingInterval, cooldownPeriod (idle time before scaling to zero) and behavior (HPA scale-up and scale-down policies).
  • Workers being scaled down drain like any shutdown; set shutdownTimeoutSeconds above your longest task, or accept that it is retried elsewhere.
  • On kind, the end-to-end suite scales a dedicated pool from 0 to 3 workers in about 16 seconds and back to 0 under a minute after the work ends.

Kubernetes tasks

kubernetesTasks:
  enabled: true
  namespace: tasks                # default: the release's namespace
  serviceAccounts: [reports-reader]   # accounts tasks may name; must exist there
  workers: {replicas: 2, slots: 20}

This adds a k8s worker pool that runs only k8s tasks. It is the only pool with a Kubernetes token, bound to a Role that may manage pods (and read their logs) in the task namespace and nothing else; shell tasks elsewhere have no credentials to read. Task pods run as a chart-made service account with no permissions and no token, unless a task names an allowed one. A NetworkPolicy lets nothing connect to task pods. Consider a dedicated namespace with Pod Security restricted and a ResourceQuota.

    instances: 3

  ingress: {enabled: true, className: nginx, host: conductor.example.com, tls: [{hosts: [conductor.example.com], secretName: conductor-tls-public}]}

Reference: GKE with Terraform

deploy/terraform/gke builds a complete production setup on Google Cloud: GKE Autopilot with private nodes and Cloud NAT, Cloud SQL Postgres 16 (regional high availability, private IP only, backups with point-in-time recovery, TLS required), KEDA and Conductor through Helm, scraped by Google Managed Prometheus. Deletion protection is on by default; state holds the database password, so use an encrypted remote backend.

cd deploy/terraform/gke
terraform init
terraform apply -var project_id=my-project \
  -var conductor_image=REGISTRY/conductor -var operator_image=REGISTRY/conductor-operator -var image_tag=TAG
$(terraform output -raw get_credentials)

Production checklist

  • A real database: CloudNativePG or a managed service, with backups you have restored once.
  • Your own secrets (or the chart's generated ones, kept); development defaults never leave a laptop.
  • TLS between components (default on Kubernetes) and in front of the API (Ingress).
  • At least two coordinators, on different nodes.
  • shutdownTimeoutSeconds sized to your tasks; idempotent side effects for the ones that may run twice.
  • Metrics scraped and the alert rules loaded (no leader, no healthy workers, a queue backing up, failures spiking, lost tasks).
  • Scoped API keys per team and namespace; the bootstrap admin key kept for administration.
