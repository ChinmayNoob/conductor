Why a workflow engine for AI

Model calls are slow, they fail in odd ways (rate limits, timeouts, malformed answers), and every token costs money. Those are exactly the properties durable workflows handle: retries with back-off, budgets, checkpoints, and a person in the loop when one is needed. In Conductor, a model call is an ordinary task, so it inherits queues, limits, cancellation, tracing and the dashboard without new machinery.

Ground rules Model output is never executed directly: drafted workflows need validation and a person to save them. API keys live in the environment, never in definitions or the database. AI features that send data to a model are opt-in per namespace, and everything sent is redacted first.

Setting up a model

Workers run model calls; the API runs the operations assistant. Give both the same settings:

Workers with a model advertise type.llm; others never receive model calls. For tests and demos, conductor mock-llm (the mock-llm Compose profile, or mockLLM.enabled in the chart) serves a scripted, free stand-in: point CONDUCTOR_LLM_BASE_URL at it.

Model calls

name: triage
inputs:
  ticket: {required: true}
budget: {max_tokens: 20000, max_cost_usd: 0.50}
steps:
  - name: classify
    llm:
      prompt: "Classify this support ticket: ${{ inputs.ticket }}"
      schema:
        type: object
        properties: {severity: {type: string, enum: [low, medium, high]}, summary: {type: string}}
        required: [severity, summary]
        additionalProperties: false
  - name: page
    depends_on: [classify]
    env: {SEVERITY: "${{ steps.classify.outputs.severity }}"}
    run: '[ "$SEVERITY" = high ] && ./page-oncall.sh || echo "no page"'
  • Structured output. With a schema, the model must return a matching JSON object, and its top-level fields become outputs that later steps use. Without one, the answer is the text output.
  • Rate limits. A provider's 429 with Retry-After sets the minimum delay before the retry. Queues can cap tokens_per_minute, enforced at dispatch.
  • Permanent errors (an invalid key, an unknown model, a bad request) fail at once instead of burning retries.
  • Standalone: conductorctl task submit -prompt "Summarize: ..." -model M -schema '{...}'.

Costs and budgets

Every model call records its input and output tokens, and its cost when the model is priced. Spend is summed per task, per run and per namespace, and shown on the run page.

People and other systems in the loop

Approval steps pause a run until someone decides, with a timeout that approves or rejects by default; rejection compensates. Signal steps pause until another system sends data, which becomes the step's outputs. Neither holds a worker while waiting. See approval and signal.

conductorctl approvals                                   # what is waiting, across runs
conductorctl workflow approve RUN sign_off -comment "checked the diff"
conductorctl workflow signal RUN payment-confirmed -data '{"ref": "pay_123"}'

Durable agents

An agent step runs a model with tools in a loop. What makes it durable is that the loop is a state machine over tasks: every model call and every tool call is its own task, created exactly once with the key agent:<run>:<turn>:<call>, and the conversation is stored as it grows.

  • Tools are shell commands. The model's arguments arrive as $ARG_<NAME> and $TOOL_ARGS, never spliced into the command, so a model can't inject shell code.
  • Limits: max_turns (default 10), max_tool_calls (50), max_duration (15m), a budget, and per-tool timeouts. Hitting one fails the step, and the run compensates.
  • Tested: the end-to-end suite kills a worker in the middle of an agent's tool call and checks that the agent finishes with each call run once, except the interrupted one.
  • The dashboard shows an agent's whole conversation, each call, its task and its cost.

The operations assistant

Opt a namespace in with conductorctl namespace set NAME -ai-assist. The assistant advises; it never acts. It doesn't change retries, and it can't save anything.

FeatureWhat it doesCommand
Failure explanationsWhen a task fails for good, a rule-based classifier labels it (transient, permanent, needs attention) with a confidence. The model then adds a likely cause and a fix from the redacted error and output. They appear on the failed task in the dashboard.conductorctl task explain ID
Ask your clusterAnswers questions using read-only lookups scoped to the namespace: task counts, tasks, a task, runs, workers, spend.conductorctl ai ask "why did yesterday's runs fail?"
Draft a workflowTurns a description into YAML, validates it with the real parser (with one repair attempt), dry runs it to show which steps start together, flags risky commands (rm -rf, curl | sh, hard-coded secrets), and asks before saving.conductorctl ai workflow "fetch A and B in parallel, then merge" -save

What leaves the cluster

Only for namespaces with ai_assist on, and only after redaction: API keys, tokens, JWTs, passwords, credentials in URLs and Conductor keys are masked. The model's reply is redacted again before it is stored. Rules decide the failure class whenever one matches; the model's words never override them.

Evaluation sets

A labelled set of real-looking failures checks the rule classifier on every test run: when a rule decides, it must be right, and cases meant for the model must not be caught by a rule. When prompts or rules change, CI runs the same set through a real model (if the repository has a key). A separate test checks that no secret reaches a prompt from any field of a task.

Known limits

  • The assistant's own spend is recorded on explanations, but doesn't count against namespace budgets.
  • Identical prompts are not cached; every call reaches the model.
  • Agents' tools are shell commands; there is no MCP client.
