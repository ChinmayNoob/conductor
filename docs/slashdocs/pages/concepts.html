Tasks

A task is one unit of work: a shell command, an HTTP call, a container, a Kubernetes pod or a model call (see task types). You submit it on its own, or a workflow, schedule or agent creates it for you. Either way it goes through the same queue, retries and limits.

Lifecycle and attempts

  • Attempts. Every dispatch increments the task's attempt number. Only a report for the current attempt is accepted. Earlier attempts are kept in the attempt history with their worker, timing, error and output: conductorctl task attempts <id>.
  • Back-off. Attempt n of a failing task waits retry_delay × 2n, capped at one hour. A model provider's Retry-After sets a minimum.
  • Permanent errors skip the remaining retries: an invalid task spec, an image that can't exist, a rejected service account, a bad model key or unknown model.
  • Lost tasks. A task whose worker stops heartbeating, or that runs past its timeout plus 30 seconds without a result, fails as lost and goes through the normal retry path.
  • Cancellation of a queued task removes it from the queue; of a running task, kills its whole process group (or deletes its pod). A late report from the cancelled attempt is ignored.
  • Dead-letter queue. Permanently failed tasks are listed with conductorctl dlq; task requeue <id> gives one a fresh set of retries, keeping its history.

What a task sees

Tasks run in a minimal environment, not the worker's: a sane PATH, HOME, TMPDIR and locale, the task's own env, and variables Conductor sets. Worker secrets such as the cluster token or database password are never visible; a worker may pass named variables through on purpose (CONDUCTOR_WORKER_PASS_ENV).

VariableValue
CONDUCTOR_TASK_IDThe task's ID
CONDUCTOR_ATTEMPTThe attempt number, unique per dispatch: use TASK_ID + ATTEMPT to de-duplicate side effects
CONDUCTOR_RETRYHow many retries came before this attempt

Output (stdout and stderr, interleaved) is captured up to 1 MB by default; beyond that the beginning and the end are kept, since errors usually show up at the end. It can be followed live while the task runs.

Delivery guarantees

Conductor delivers tasks at least once. If a worker dies mid-task, Conductor cannot know whether the task's side effects happened, so it runs the task again elsewhere. Design side effects to be safe to repeat:

  • Use CONDUCTOR_TASK_ID (stable across retries) as an idempotency key for the systems you call: a payment provider's idempotency header, a unique constraint, an upsert.
  • Submit with an idempotency_key so a client retry doesn't create a second task. The second submission returns the first task with HTTP 200 instead of 201.
  • Workflow runs and schedules use the same mechanism internally: a schedule slot fires once, and an agent's tool call is created once per call.
What is guaranteed A task is never lost and never stuck: it ends COMPLETED, FAILED or CANCELLED. Only one result is recorded per task (attempt fencing). It may run more than once.

Queues

Every task belongs to a queue (default unless set). Queues exist implicitly; give one settings to limit it:

conductorctl queue set emails -concurrency 5 -rate 100 -per 60   # at most 5 at once, 100 per minute
conductorctl queue set emails -pause                             # stop dispatching; submissions still queue
conductorctl queue list
SettingEffect
concurrency_limitAt most this many of the queue's tasks run at once
rate_limit per rate_period_secondsAt most this many dispatches per sliding window
tokens_per_minuteFor llm tasks: at most this many model tokens dispatched per minute
pausedNothing is dispatched until resumed

Limits are enforced inside the dispatch query, also within one batch, so they hold exactly even under load.

Priority and aging

Priority runs from 1 (most urgent) to 10. Strict priority would let a steady stream of urgent tasks starve everything else, so waiting tasks age: a task gains one priority level per aging interval (60 seconds by default, CONDUCTOR_PRIORITY_AGING). Concretely, tasks are ordered by scheduled_at + priority × interval: a priority-9 task that has waited nine minutes goes before a priority-1 task submitted just now. Set the interval to 0 for strict priority.

Labels and worker pools

Workers advertise labels: their own (CONDUCTOR_WORKER_LABELS=gpu=true,region=eu) plus one per task type they can run (type.shell, type.http, type.container, type.k8s, type.llm). A task runs only on a worker that has every label it requires, including its type's. Tasks that require labels no worker has simply wait.

A dedicated worker also names labels a task must require to run there (CONDUCTOR_WORKER_EXCLUSIVE=pool), like a Kubernetes taint. Without it, a worker with gpu=true would also run every plain task. In the Helm chart, each worker pool gets a pool=<name> label, and a dedicated pool takes only tasks with labels: {pool: <name>}.

conductorctl task submit -cmd './train.sh' -label gpu=true          # any worker with gpu=true
conductorctl task submit -cmd './train.sh' -label pool=gpu          # only the dedicated gpu pool

A worker can also be limited to some task types (CONDUCTOR_WORKER_TASK_TYPES=k8s). The chart uses this for the pool that runs Kubernetes tasks, which then runs no task code of its own.

Namespaces

Namespaces isolate teams. Each has its own tasks, workflow definitions, runs, schedules, queues and API keys. A key belongs to one namespace; admin keys may act in any (X-Conductor-Namespace, or conductorctl -n). default always exists.

conductorctl namespace create team-a -max-pending 1000 -max-concurrency 20
conductorctl apikey create team-a-ci -namespace team-a       # prints the key once
conductorctl -n team-a task list
QuotaEffect

Workflows, schedules and waits

A workflow definition is a named, versioned DAG of steps written in YAML. A workflow run executes one version with some inputs; each step becomes a task (or a wait). If a step fails for good, completed steps are compensated: their undo actions run in reverse order, like a saga. See the workflow reference.

A schedule starts a task or a workflow on a cron expression in a time zone, once per slot, with a misfire policy for slots missed while Conductor was down.

Approval and signal steps pause a run until a person approves or rejects, or another system sends data, holding no worker meanwhile. Agent steps let a model call tools in a loop, each call a checkpointed task. See AI features.
