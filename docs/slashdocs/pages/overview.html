What Conductor is

Conductor is a self-hosted engine for running background work reliably: single tasks, multi-step workflows, scheduled jobs and AI agents. You describe the work; Conductor queues it, hands it to workers, retries it when it fails, undoes completed steps when a later one cannot succeed, and keeps a record of every attempt.

Its defining choice is that Postgres is the only dependency. There is no Kafka, Redis, etcd or ZooKeeper to run: the queue, the workflow state, leader election and the wake-up signals all live in one Postgres database, using SELECT … FOR UPDATE SKIP LOCKED, advisory locks and LISTEN/NOTIFY. If you already operate Postgres, you can operate Conductor.

In one sentence Durable workflows, retries, sagas and AI agents, on nothing but Postgres, set up in five minutes.

What it does

Tasks

Shell commands, HTTP calls, containers, Kubernetes pods and model calls, with retries, exponential back-off, timeouts, priorities, delays and cancellation that kills the whole process tree.

Workflows

DAGs written in YAML: steps run in parallel where they can, pass outputs to each other, and compensate (undo) in reverse order when a later step fails. Each run keeps the definition version it started with.

Scheduling

Cron schedules with time zones and a misfire policy; queues with concurrency and rate limits; priority aging so nothing starves; label-based routing to the right workers.

AI steps

Model calls with token and cost budgets, approval steps that wait for a person, signals from other systems, and agents whose every model and tool call is a checkpointed task.

High availability

Several coordinators with automatic leader election through Postgres; every write is fenced by an epoch and every result by an attempt number, so a stale leader or worker can never change anything.

Observability

A web dashboard with live workflow diagrams, Prometheus metrics on every process, OpenTelemetry traces from the API call into the task, live task output and the history of every attempt.

Kubernetes

A Helm chart for a highly available cluster, worker pools that scale on queue depth down to zero, tasks that run as their own locked-down pods, and an operator for GitOps.

Secure by default

API keys stored as hashes, namespaces with quotas, mutual TLS between components, tasks that run unprivileged with a minimal environment, and inputs that can never become shell code.

How it works, briefly

The API authenticates requests and records tasks and workflow runs in Postgres. The coordinator that holds the leadership lock claims due tasks, sends them to workers with free capacity, records results, drives workflows forward and fires schedules. Workers run tasks and report back. Everything a coordinator knows can be rebuilt from Postgres, which is what makes failover safe. The architecture page goes through each step.

Guarantees, honestly stated

  • At-least-once delivery. A task whose worker dies is run again elsewhere, so a task can run more than once. Every attempt gets CONDUCTOR_TASK_ID and CONDUCTOR_ATTEMPT, and submissions take an idempotency key, so side effects can be made safe. See delivery guarantees.
  • No lost work. Killing a worker, the leader coordinator, both coordinators, or restarting Postgres loses no task and leaves none stuck; a nightly chaos suite checks exactly this.
  • Stale actors change nothing. A deposed leader cannot write (epoch fencing), and a report from an old attempt, say from a worker that was partitioned away, is ignored (attempt fencing).
  • Compensation runs where it should, and only there. When a workflow fails, every completed step with a compensation is undone, in reverse dependency order.

When to use it, and when not

Good fitLook elsewhere
Background jobs that must not be lost: emails, exports, billing runs, syncsSub-millisecond job queues at hundreds of thousands per second (a dedicated broker will win)
Multi-step processes that need undo: orders, bookings, provisioningWorkflows written as long-running code with replay (Temporal's model)
Scheduled jobs that should run once per slot, even across restartsData pipelines that need a dataset-aware scheduler and lineage (Airflow, Dagster)
AI agents and model calls that are slow, flaky and expensiveStream processing
Teams that want one dependency they already run: PostgresEnvironments where Postgres is not an option

Project status

Conductor is pre-1.0 and developed in public phases: a working scheduler with sagas, production basics (CI, migrations, auth, TLS), a real scheduler (YAML DAGs, cron, queues, task types), distributed-systems depth (HA, fencing, benchmarks, chaos tests), observability and a dashboard, AI-native execution, and Kubernetes. The open-source launch (a new name, releases with published images, a docs site) is next. Container images are not published yet: build them from the repository, as the quickstart does.

The repository holds the roadmap (plan.md), an engineering log with diagrams of how each phase was built (DEVLOG.md), and design decision records (docs/adr).
