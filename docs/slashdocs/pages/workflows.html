The shape of a definition

A workflow definition is YAML (or JSON) describing a directed acyclic graph of steps. Each step runs one action, optionally after others, and may say how to undo itself.

name: order_pipeline                 # lowercase letters, digits, '-' or '_'
description: Reserve, charge, ship.
inputs:
  order_id: {required: true}
  amount: {default: "100"}
defaults:                            # for every step, unless the step says otherwise
  retries: 1
  retry_delay: 2s
  timeout: 1m
budget: {max_tokens: 50000}          # optional cap on model spend for the run
steps:
  - name: validate
    run: echo "customer=cus_$INPUT_ORDER_ID" >> "$CONDUCTOR_OUTPUT"

  - name: reserve_stock
    depends_on: [validate]
    run: echo "reservation=res_$INPUT_ORDER_ID" >> "$CONDUCTOR_OUTPUT"
    compensate: echo "releasing $OUTPUT_RESERVATION"

  - name: charge_card
    depends_on: [validate]
    env:
      CUSTOMER: "${{ steps.validate.outputs.customer }}"
    run: ./charge.sh "$CUSTOMER" "$INPUT_AMOUNT"
    compensate: ./refund.sh

  - name: ship
    depends_on: [reserve_stock, charge_card]
    retries: 0
    run: ./ship.sh
conductorctl workflow apply -f order_pipeline.yaml     # a new version only if it changed
conductorctl workflow start order_pipeline -input '{"order_id": "A1"}' -wait

Unknown fields are rejected, so a typo such as depend_on fails loudly instead of silently doing nothing. The whole definition is validated when you apply it: names, the graph, every expression, every step's settings.

Top-level fields

name (required)
1 to 63 characters: lowercase letters, digits, - or _, starting with a letter or digit. Unique per namespace; applying again creates a new version.
description
Shown in listings and the dashboard.
inputs
Declared inputs: each may be required: true, have a default, and a description. When inputs are declared, a run may pass only those. Without declarations, any input is accepted.
defaults
Step options applied to every step: retries, retry_delay, timeout, priority, queue, labels.
budget
max_tokens and/or max_cost_usd for model calls across the run. Going over fails the run, which compensates like any failure.
steps (required)
At least one step.

Inputs

A run's inputs reach every step as environment variables named INPUT_<NAME> (upper-cased), and expressions can use them as ${{ inputs.name }}. Strings pass through as they are; numbers, booleans, lists and objects become their JSON text.

inputs:
  user_id: {required: true, description: The customer}
  region: {default: eu}
  dry_run: {default: "false"}

Starting a run without a required input, or with an undeclared one, is refused with HTTP 400 before anything runs.

Durations are Go durations (90s, 5m, 1h30m) or whole seconds (90). Precedence is: built-in defaults, then the workflow's defaults, then the step's own settings.

Expressions

Values computed at run time are written ${{ … }}. Three references exist:

ExpressionValue
${{ inputs.NAME }}A run input
${{ steps.STEP.outputs.KEY }}An output of an earlier step; STEP must be a dependency, direct or indirect
${{ workflow.id }}The run's ID

Expressions are allowed in env values, http.url, http.body and headers, container.command, k8s.command and k8s.args, llm.prompt and llm.system, approval.message, and agent.prompt and agent.system.

Never in run Expressions are rejected in shell commands (run) and in agent tool commands. Put the value in env and use $VARIABLE in the command instead. Values then reach the shell only as data, so an input like 1; rm -rf / can never be interpreted as code. This is the design, not a limitation: there is no injection to defend against. 
- name: notify
  depends_on: [charge_card]
  env:
    CHARGE: "${{ steps.charge_card.outputs.charge_id }}"
    RUN: "${{ workflow.id }}"
  run: ./notify.sh "$CHARGE" "$RUN"

Outputs

A step publishes outputs by appending key=value lines to the file named by $CONDUCTOR_OUTPUT; later lines win. Keys are letters, digits, _ and -, starting with a letter or _. Other steps read them through ${{ steps.STEP.outputs.KEY }}, and the step's own compensation sees them as OUTPUT_<KEY>.

run: |
  id=$(./create_reservation.sh)
  echo "reservation=$id" >> "$CONDUCTOR_OUTPUT"

Other types produce outputs too: an http step returns status and body, an llm step text or its schema's fields, an approval comment and decided_by, a signal its payload's fields, an agent answer. Outputs are limited to 64 KB per step (4 KB for k8s steps).

Compensation

When a step fails for good, or the run is cancelled, Conductor cancels the steps still running, skips the ones not yet started, and runs the compensation of every completed step, in reverse dependency order: a step is undone only after everything that depended on it has been undone.

compensate: ./refund.sh "$OUTPUT_CHARGE_ID"          # shorthand: a shell command

compensate:                                          # or any action
  type: http
  http:
    method: POST
    url: https://payments.internal/refunds
    body: '{"charge": "${{ steps.charge_card.outputs.charge_id }}"}'
  • A compensation runs with the step's queue, labels and retry settings, and sees the step's outputs as OUTPUT_<KEY>.
  • Steps without compensate are left as they are.
  • A compensation that fails after its retries marks the step COMPENSATION_FAILED; the run still ends FAILED, and the dashboard shows what could not be undone.
  • Make compensations idempotent, like any task: they are delivered at least once.

Versions

Applying a definition stores it as a new version only if it differs from the latest one. A run takes a snapshot of the version it starts with, so changing a workflow never affects runs in flight. Start an older version explicitly when you need to:

conductorctl workflow defs                         # names and latest versions
conductorctl workflow show order_pipeline -version 3
conductorctl workflow start order_pipeline -version 3 -input '{"order_id": "B7"}'

Running and controlling runs

conductorctl workflow start NAME [-input JSON] [-version N] [-key IDEMPOTENCY_KEY] [-wait]
conductorctl workflow get RUN_ID                  # status, each step, outputs, errors
conductorctl workflow watch RUN_ID                # follow it until it finishes
conductorctl workflow cancel RUN_ID               # cancel running steps, compensate completed ones
conductorctl workflow list -limit 20

A run started with an idempotency key (-key) is created once: starting it again with the same key returns the first run. The dashboard draws each run as a live diagram: green steps done, the failed step marked with its error, and compensation drawn back along the route.

Validation rules

  • Step names are unique; every depends_on names an existing step, listed once.
  • The graph has no cycles. A cycle is reported with its path, e.g. a -> b -> a.
  • Each step has the settings of its type and no others: a shell step can't have http, an http step needs http.url, and so on.
  • Expressions refer to declared inputs, to steps that are dependencies, or to workflow.id.
  • env names are valid environment variable names.
  • Retries, delays and timeouts aren't negative; priority is 1 to 10; queue names follow the naming rule.

Every problem is reported at once, so one apply shows everything to fix.

Patterns

Fan out and in

steps:
  - {name: fetch_a, run: ./fetch.sh a}
  - {name: fetch_b, run: ./fetch.sh b}
  - {name: fetch_c, run: ./fetch.sh c}
  - name: merge
    depends_on: [fetch_a, fetch_b, fetch_c]      # starts when all three completed
    run: ./merge.sh

A human gate

  - name: approve_refund
    depends_on: [assess]
    type: approval
    approval:
      message: "Refund ${{ steps.assess.outputs.amount }} to ${{ inputs.customer }}?"
      timeout: 24h
      on_timeout: reject        # rejecting fails the step, and completed steps are compensated

Routing a step to special workers

  - name: render
    labels: {pool: gpu}          # only the dedicated gpu pool
    queue: rendering             # which may have its own concurrency limit
    timeout: 30m
    run: ./render.sh
