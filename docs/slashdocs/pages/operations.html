High availability

  • Coordinators: run at least two, on different machines. One leads through a Postgres advisory lock; standbys take over within about a second of the leader's death (0.5 to 1.6 s in the end-to-end suite, on Compose and Kubernetes). Nothing in flight is lost: workers keep running their tasks and report to the new leader.
  • API: stateless; run two or more behind a load balancer. On Kubernetes it delays shutdown until endpoints stop routing to it.
  • Workers: run enough to survive losing one; tasks of a dead worker are retried elsewhere after 30 seconds without heartbeats.
  • Postgres is the one component everything depends on. Make it highly available the way you do for other Postgres databases: CloudNativePG, a managed service with a standby, or Patroni. A Postgres restart is survived (the chaos suite restarts it under load), but nothing is dispatched while it is down.
conductorctl cluster           # the leader, its epoch, and every coordinator (admin)
conductorctl workers           # every worker: address, labels, slots, running, health

Scaling and capacity

Throughput is bounded by Postgres, not by workers: each task costs the leader about four writes (insert, a share of a batch claim, started, finished). On a laptop (everything in one Docker VM), measured with conductor-bench:

Read these as a floor: Postgres, coordinators, the API, up to 50 workers and the load generator shared one laptop's CPUs. Sustained rates with ingest and dispatch together sit between 200 and 400 tasks/s on that machine; a dedicated database raises everything. make bench (or scripts/bench.sh) reproduces the numbers on yours.

  • More slots, not just more workers. A worker runs CONDUCTOR_WORKER_SLOTS tasks at once. For tasks that mostly wait (HTTP calls, model calls, k8s pods), give workers many slots.
  • Autoscale on demand on Kubernetes with KEDA (deploying).
  • Protect Postgres with queue concurrency and rate limits rather than by starving workers.
  • Keep outputs small: output is stored on the task row (1 MB by default, CONDUCTOR_MAX_OUTPUT_BYTES).

Upgrades

  • Migrations are embedded in the binary and applied on startup, under an advisory lock so starting several components at once is safe. They are forward-only: back up the database before upgrading, and roll back by restoring it.
  • Rolling restarts are safe. Coordinators: start the new one before stopping the old (the chart surges); if the leader stops, a standby takes over. Workers: SIGTERM makes them drain; tasks that don't finish within the shutdown timeout are killed and retried. API: stateless.
  • Workflow runs in flight keep the definition version they started with; applying new definitions never affects them.
  • The end-to-end suite restarts every component under load (TestRollingRestartLosesNothing) and requires that no task or run is lost and no API request fails.

Traces and logs

Set OTEL_EXPORTER_OTLP_ENDPOINT to export OpenTelemetry traces over OTLP gRPC (the standard OTEL_* variables apply). A task's trace runs from the HTTP request, through its wait in the queue (the trace context is stored on the task), the dispatch and the worker, into the task itself, which receives TRACEPARENT. A workflow's steps share their run's trace. Logs are structured (CONDUCTOR_LOG_FORMAT=json or text) and carry task, workflow and worker IDs.

Troubleshooting

A task stays QUEUED
Check, in order: is there a leader (conductorctl cluster)? Does any healthy worker have every label the task requires, including its type (conductorctl workers; for k8s and llm tasks, is such a worker configured)? Is the queue paused or at its concurrency or rate limit (conductorctl queue list)? Is the namespace at its concurrency quota? Is it scheduled for later (scheduled_at)? A dedicated pool takes only tasks that require its pool label.
A task failed
conductorctl task attempts ID shows every attempt's worker, error and output; task logs ID the last one. With ai_assist, task explain ID suggests a cause and fix. Fix it, then task requeue ID for a fresh set of retries.
Tasks are "lost"
A worker stopped heartbeating (crash, OOM kill, network) or a task ran past its timeout plus 30 s. Lost tasks are retried; look at the worker's logs and restarts, and at task timeouts.
A run is stuck RUNNING
It is usually waiting: an approval (conductorctl approvals), a signal, or a step whose task is queued (see above). The run page shows which.
No leader
Coordinators can't reach Postgres, or none is running. Check their logs and /readyz.
"not the leader" errors in logs
Normal during an election: clients follow the redirect. Persistent ones mean clients can't reach the leader's advertised address (CONDUCTOR_COORDINATOR_ADVERTISE_ADDR).
A k8s task fails with ImagePullBackOff, or times out "never scheduled"
The image or its pull secret is wrong, or no node fits the pod's resources and node selector. The error says which.

Backup and restore

Postgres holds everything: tasks and their history, definitions, runs, schedules, keys. Back it up like any production database (CloudNativePG or managed-service backups with point-in-time recovery, or pg_dump). After a restore, start the coordinators: the leader rebuilds its state from the database, and tasks that were running at backup time are recovered as lost and retried.
