Before you start

You need Docker (with Compose v2) and Go 1.24 or newer to build the command-line client. Container images are not published yet, so every option below builds Conductor from a checkout of the repository:

git clone https://github.com/ChinmayNoob/conductor.git
cd conductor
go build -o bin/conductorctl ./cmd/conductorctl    # the command-line client

Pick one of three ways to run it. All three end with the same API on a local port and the same commands.

OptionRunsBest for
Docker ComposePostgres, two coordinators, the API and three workers, as containersTrying everything, including failover
One processCoordinator, API and a worker in one conductor dev process, against any PostgresDeveloping against Conductor
Kubernetes (kind)The Helm chart on a local three-node cluster, with autoscaling and the operatorTrying the Kubernetes features

Option A: Docker Compose

docker compose up -d --build --scale worker=3
export CONDUCTOR_API_KEY=insecure-dev-api-key       # the development default
bin/conductorctl workers                            # three healthy workers

The API listens on http://localhost:8081, which is also conductorctl's default (CONDUCTOR_URL changes it). The dashboard is at http://localhost:8081/ui/; sign in with the same key.

Development secrets The Compose file falls back to insecure, well-known values for the cluster token and the API key. Before running it anywhere but your own machine, copy .env.example to .env and set CONDUCTOR_CLUSTER_TOKEN and CONDUCTOR_API_KEY. Components log a warning while they run with development secrets.

Optional extras are Compose profiles:

docker compose --profile containers up -d          # a worker that can run container tasks (mounts the Docker socket)
docker compose --profile mock-llm up -d            # a scripted stand-in model, for llm and agent steps
OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4317 docker compose --profile observability up -d
                                                   # Prometheus :9091, Grafana :3000, Jaeger :16686

Option B: one process

conductor dev runs the coordinator, the API and one worker in a single process. It needs only a Postgres database; the Compose stack's Postgres on port 5433 works:

docker compose up -d postgres
POSTGRES_PORT=5433 go run ./cmd/conductor dev
export CONDUCTOR_API_KEY=insecure-dev-api-key

It creates its schema on start (migrations run automatically, guarded by an advisory lock), generates a random cluster token, and prints the API address and key. Point POSTGRES_HOST, POSTGRES_USER, POSTGRES_PASSWORD and POSTGRES_DB at any other database.

Option C: Kubernetes on kind

With kind, kubectl and helm installed:

make kind-up                                       # or ./scripts/kind-up.sh
export CONDUCTOR_URL=http://localhost:30081
export CONDUCTOR_API_KEY=$(./scripts/kind-up.sh --api-key)

This creates a three-node cluster, builds the images and loads them into it, installs KEDA, and installs the chart with two coordinators, two API replicas, three workers, a worker pool that scales from zero, Kubernetes tasks, a scripted model and the operator. Delete it all with kind delete cluster --name conductor. Deploying covers real clusters.

Your first task

bin/conductorctl task submit -cmd 'echo "hello from $(hostname)"' -wait

-wait waits for the result and prints the task: its status (COMPLETED), retries and output. Without -wait you get the task back immediately; -o json makes any command print JSON:

id=$(bin/conductorctl -o json task submit -cmd 'sleep 5; echo done' | jq -r .id)
bin/conductorctl task logs $id -f          # follow the output live
bin/conductorctl task get $id
bin/conductorctl task list -status COMPLETED -limit 5

A failing command is retried with exponential back-off (three retries, 60 seconds apart and doubling, by default). Try one that fails and look at its attempts:

bin/conductorctl task submit -cmd 'echo trying; exit 1' -retries 2 -retry-delay 1
bin/conductorctl task attempts <id>       # every attempt, which worker ran it, and why it failed
bin/conductorctl dlq                        # permanently failed tasks

Your first workflow

Save this as hello.yaml:

name: hello
inputs:
  name: {required: true}
steps:
  - name: greet
    run: |
      echo "Hello, $INPUT_NAME"
      echo "greeting=Hello, $INPUT_NAME" >> "$CONDUCTOR_OUTPUT"
  - name: shout
    depends_on: [greet]
    env:
      GREETING: "${{ steps.greet.outputs.greeting }}"
    run: echo "$GREETING" | tr a-z A-Z
bin/conductorctl workflow apply -f hello.yaml
bin/conductorctl workflow start hello -input '{"name": "Ada"}' -wait

Three things to notice. Inputs reach commands as environment variables (INPUT_NAME), never spliced into the command text. A step publishes outputs by appending key=value lines to the file named by $CONDUCTOR_OUTPUT. A later step reads them through a ${{ }} expression in its env, and only a step that depends on it (directly or not) may.

See a saga undo itself

The bundled order_pipeline workflow validates an order, reserves stock and charges the card in parallel, then ships. Ask it to fail at shipping:

bin/conductorctl workflow start order_pipeline \
  -input '{"order_id": "A1", "fail_shipping": "true"}' -wait

The run ends FAILED, and both parallel branches show COMPENSATED: the charge was refunded and the reservation released, each compensation seeing its own step's outputs. Open the run in the dashboard to watch it as a diagram, with the failed step and the undo drawn back along the route.

A schedule

bin/conductorctl schedule create hello-hourly -cron '@hourly' -workflow hello -input '{"name": "cron"}'
bin/conductorctl schedule trigger hello-hourly     # fire it now
bin/conductorctl schedule list
