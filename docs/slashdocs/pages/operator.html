Workflows as Kubernetes resources

The operator lets workflows, runs and schedules live in Git next to the rest of your manifests and ship with kubectl apply, Argo CD or Flux. It watches three resource kinds in the conductor.dev/v1alpha1 API group and applies them to Conductor through the HTTP API, the same way conductorctl would. It never touches the database.

KindShort nameDoesOn delete
WorkflowcwfKeeps a definition applied; a changed spec becomes a new versionLeaves the definition's versions, which past runs refer to
WorkflowRuncwrStarts one run, exactly once, and follows it until it finishesCancels it if unfinished (and compensates), unless keepRunningOnDelete
SchedulecschKeeps a cron schedule applied, history includedDeletes the schedule

Installing

helm upgrade --install conductor deploy/helm/conductor -n conductor --set operator.enabled=true \
  --set operator.image.repository=REGISTRY/conductor-operator --set operator.image.tag=TAG

The chart installs the CustomResourceDefinitions (kept on uninstall, since deleting a CRD deletes every resource of its kind), a ClusterRole limited to these three kinds (or Roles in operator.watchNamespaces only), leader election, and the operator itself, which uses the bootstrap admin key. Several replicas can run; one leads.

Which Conductor namespace

Each resource goes to the Conductor namespace named after its Kubernetes namespace, which the operator creates if needed: resources in team-a land in Conductor's team-a. Same-named resources in two Kubernetes namespaces therefore never collide. spec.conductorNamespace picks another; operator.defaultNamespace sends every resource that names none to one Conductor namespace (then keep names unique across Kubernetes namespaces).

Workflow

apiVersion: conductor.dev/v1alpha1
kind: Workflow
metadata:
  name: nightly-report
spec:
  definition:                 # exactly what `conductorctl workflow apply` takes
    inputs:
      day: {default: yesterday}
    steps:
      - name: build
        type: k8s
        k8s: {image: ghcr.io/acme/reports:1.4, args: [build, "${{ inputs.day }}"], memory: 512Mi}
      - name: publish
        depends_on: [build]
        run: ./publish.sh "$REPORT"
        env: {REPORT: "${{ steps.build.outputs.report }}"}
spec.definition
The workflow definition (see the reference). Its name defaults to the resource's name. Conductor validates it; problems show in the Ready condition.
spec.conductorNamespace
Optional, as above.
status.name, status.version
The definition in Conductor and its current version.

WorkflowRun

apiVersion: conductor.dev/v1alpha1
kind: WorkflowRun
metadata:
  name: nightly-report-backfill-0901
spec:
  workflow: nightly-report     # the definition's name in Conductor
  version: 0                   # 0 = the latest
  input: {day: "2026-09-01"}
  keepRunningOnDelete: false
  • Exactly once. The run is started with the resource's UID as its idempotency key, so a lost status update or an operator restart can't start a second run. A finished WorkflowRun, including one that could never start, is never started again.
  • Immutable. The spec can't change (a validation rule refuses it); create another WorkflowRun to run again.
  • Any order. If its workflow doesn't exist yet, it waits (Ready=False, reason Waiting) and checks again.
  • Status follows the run: runID, phase (RUNNING, COMPENSATING, COMPLETED, FAILED, CANCELLED), steps, error, startTime, completionTime. Unfinished runs are checked every few seconds (--poll-interval).

Schedule

apiVersion: conductor.dev/v1alpha1
kind: Schedule
metadata:
  name: nightly-report
spec:
  cron: "0 3 * * *"            # or @hourly, @every 30s
  timezone: Europe/Berlin      # default UTC
  misfirePolicy: run_once      # skip (default), run_once or catch_up
  suspend: false
  workflow: {name: nightly-report, input: {day: yesterday}}
  # or a task instead of a workflow:
  # task: {command: "./cleanup.sh", queue: maintenance}
  • Exactly one of workflow and task (a validation rule checks). A task is decoded strictly: a misspelled field is an error, not silently dropped.
  • Applied with PUT /v1/schedules/{name}, which keeps the schedule's run history and pending run unless the timing changed. suspend: true pauses it; resuming starts from now.
  • A schedule of a workflow that doesn't exist yet waits for it.
  • Status: nextRunTime, lastRunTime, lastRunID, lastError, refreshed on every resync (--resync, 5 minutes).
  • Moving it to another Conductor namespace removes it from the old one first, so it can't keep firing there.

Every resource has a Ready condition:

ReasonMeaningWhat happens
Applied / StartedIn Conductor, as specifiedRe-applied on every resync, repairing drift
InvalidConductor rejected the spec; the message says whyNot retried until the spec changes
WaitingA run or schedule whose workflow doesn't exist yetChecked again every 10 seconds
UnreachableConductor's API failedRetried with back-off

GitOps with Argo CD

deploy/argocd is an app-of-apps that installs Conductor and the workflows that run on it, in order:

kubectl patch configmap argocd-cm -n argocd --type merge --patch-file deploy/argocd/health.yaml
kubectl create namespace conductor
kubectl create secret generic conductor-auth -n conductor \
  --from-literal=cluster-token=$(openssl rand -hex 32) --from-literal=api-key=cnd_$(openssl rand -hex 32)
kubectl apply -n argocd -f deploy/argocd/root.yaml
  • Bring your own secrets. Argo CD renders charts with helm template, where the chart can't read back secrets it generated, so it would make new ones on every sync. The example sets auth.existingSecret (created once, or from a secret manager with External Secrets) and tls.existingSecret (from cert-manager), and uses CloudNativePG rather than the dev database.
  • Health checks (health.yaml) teach Argo CD the operator's resources: a Workflow or Schedule is Healthy once applied and Degraded if rejected; a WorkflowRun is Progressing while it runs, Healthy when it completed, Degraded when it failed or was cancelled.
  • KEDA owns replicas of autoscaled pools; the Application ignores differences in /spec/replicas.
  • A workflow change is then a pull request: edit the file, merge, and the operator applies the new version. Runs already in flight keep the version they started with.

The example was run end to end on kind: the chart synced from the repository onto CloudNativePG, the operator applied the workflow and schedule, and firing the schedule scaled a worker pool from zero and ran a pod step whose output fed the next step.
