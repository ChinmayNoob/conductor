Principles

Conductor runs other people's commands, so it is built to be safe by default rather than safe once configured:

  • Every API request and every call between components is authenticated.
  • Inputs never become code: values reach commands only as environment variables.
  • Tasks run unprivileged, with a minimal environment, and never see Conductor's own secrets.
  • Privileges that are dangerous (the Docker socket, Kubernetes credentials) are opt-in and isolated.
  • Nothing leaves the cluster for a model unless a namespace opts in, and then only redacted.

API keys

  • Clients send Authorization: Bearer <key>. Keys are random (256 bits) with a recognisable cnd_ prefix, so secret scanners can find leaked ones.
  • Only a SHA-256 hash of each key is stored; the key itself is shown once, when created. Listings show a short prefix.
  • CONDUCTOR_API_KEY creates the first admin key on startup. Create scoped keys per team or service and keep the admin key for administration:
conductorctl apikey create billing-ci -namespace billing     # acts only in "billing"
conductorctl apikey create ops -admin                        # any namespace, plus workers, cluster, keys
conductorctl apikey list
conductorctl apikey revoke KEY_ID

The dashboard signs in with a key and acts with exactly its permissions. Components warn at startup while they use the development defaults (insecure-dev-…).

Namespaces and quotas

A non-admin key sees and touches only its own namespace: its tasks, definitions, runs, schedules and queues. Quotas (max_pending_tasks, max_concurrency, daily model tokens and cost) stop one team from starving or bankrupting another. See namespaces.

No injection by construction

Workflow inputs, step outputs and model answers are data. They reach shell commands only as environment variables: ${{ }} expressions are rejected in run and in agent tool commands, so echo "$INPUT_NAME" prints 1; rm -rf / instead of running it. Agents receive the model's tool arguments the same way ($ARG_<NAME>). For k8s tasks, command, args and environment are escaped so Kubernetes' $(VAR) expansion can't read other variables. The end-to-end suite submits a malicious input and checks that nothing it describes ran.

Kubernetes credentials

Creating pods needs a token, and a shell task runs as its worker's user, so it could read any token its worker has. The Helm chart therefore gives Kubernetes tasks a pool of their own that runs only k8s tasks (no task code), and that pool is the only one with a token: a Role limited to pods and their logs in the task namespace. Every other pool mounts none, and the chart refuses a pool mixing k8s with shell or container. Tasks may name only service accounts listed in kubernetesTasks.serviceAccounts; anyone who can submit tasks gets what those accounts can do, so keep the list short and the accounts narrow.

Secrets

  • Conductor's own (cluster token, admin key, database password, TLS keys, model keys) live in the environment or Kubernetes Secrets, never in the database or in task definitions.
  • Your tasks' secrets: don't put them in task env or workflow definitions, which are stored in Postgres and visible to anyone with a key for the namespace. Give the worker pool the secret (a Kubernetes Secret through extraEnv) and allow it through with passEnv; or have tasks fetch it from a secret manager with their own identity.
  • Output is stored as written. Avoid printing secrets; the operations assistant redacts before anything is sent to a model, but stored output isn't redacted.

Network policies

The chart's NetworkPolicies (on by default) make each component accept only what it needs: coordinators accept the API and workers, workers accept coordinators, the dev database accepts coordinators and the API (and KEDA's namespace when autoscaling), task pods accept nothing. The API accepts anyone unless networkPolicy.apiFrom restricts it (the operator and helm test stay admitted); /metrics accepts anyone unless networkPolicy.metricsFrom restricts it. Egress is open, since workers call arbitrary HTTP endpoints and the database may be outside the cluster.

AI features

Model calls you write (llm steps, agents) send what you put in their prompts. The operations assistant sends task data only for namespaces with ai_assist on, after redacting API keys, tokens, JWTs, passwords and credentials in URLs; it can only read (scoped to the namespace) and can't save anything. Drafted workflows are validated and scanned for risky commands, and a person has to save them.

Reporting a vulnerability

Until the project publishes a security policy with its open-source launch, report vulnerabilities privately to the maintainer through GitHub, not in a public issue.
